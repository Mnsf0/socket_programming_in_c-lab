as we know the some functions like `recv()` and `fgets()` are blocking function, means the program will stop in these functions until they get any data then the code will resume work.

### why we consider it as problem?
simply conjure up this scenario with me, what if the other side have a problem and never send data? what if for some issue on the connection the data interrpted for some reason? what if the other side didn't send any thing and get distracted by something while keeping the connection open(as some chat app for example) for all the previous cases if that happened the connection will get stuck on `recv()` and it won't keep going and read the rest of the code and the connection will remian open and it won't get closed.

### how this could use in malicious way?
imagen this scenario with me, the attacker start a connection and they should send data, but they didn't do it? what gonna happen? nothing just a try to abuse the resource of your app or website and distracted the connection and this what we call `Slowloris HTTP DoS attack` 

### Solution
`SO_RCVTIMEO` is a socket option that tells the kernel:  if I call `recv()` and no data has arrived within this many seconds, stop waiting and return an error instead of blocking forever

### Code
```c
struct timeval {
    time_t tv_sec;   // seconds
    suseconds_t tv_usec; // microseconds
};
```
```c
    struct timeval tv;
    tv.tv_sec = RECV_TIMEOUT_SEC;
    tv.tv_usec = 0;

```
it's just a configuration for the time you want to wait for 

```c
 if (setsockopt(sockdf, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv)) == -1) {
        perror("[-] setsockopt failed");
        close(sockdf);
        exit(8);
    }
```
here we apply the time interval we set it up before.

```c
(n = recv(sockdf, buf + total, cap - total, 0)) > 0)
```

here is where the countdown starts — but not just once for the whole program. **every time** this line runs (each loop iteration), the kernel starts a **fresh 10-second countdown for that specific call**. so if the server sends a small chunk every 8 seconds, each `recv()` call succeeds within its own window and the timer just resets each time. if 10 seconds pass with nothing arriving, `recv()` itself already returns `-1` right here — the timeout already happened at this line, before we even get to the next one.

c

```c
     if (errno == EAGAIN || errno == EWOULDBLOCK)
```

this line doesn't cause the timeout or turn anything off — the timeout already occurred one line earlier when `recv()` returned `-1`. what this line does is **diagnose why** it returned `-1`: was it because of our 10-second timeout, or because of some other error (like the connection getting reset)? based on that answer, we decide what message to print and whether to `exit()` — but that decision is ours, the check itself is just telling us what happened.
