`int listen_socket, comminucation_sock;`

#### why we need two sockets? 
- **`listen_socket`:** Listens strictly for incoming **connection requests** (TCP handshakes), not actual messages.
    
- **`comminucation_sock`:** Created by `accept()` when a client connects, used exclusively for data transfer (`send()`, `recv()`).

`socklen_t size_comminucation_sock = sizeof(comminucation_address);`
#### why we make only one socklen_t not for both?
because:
- **Listening Socket (`bind`): You tell the system the size.** You set up the server address yourself, so you already know how big it is. You just tell the system: _"Here is my address, and it is 16 bytes long."_ You pass `sizeof(...)` directly because the system only needs to **read** your number.
    
- **Communication Socket (`accept`): The system tells YOU the size.** You don't know who is connecting or what kind of address they have. So, you give the system an empty card and say: _"Put the client's info here, and **write down on this card** how many bytes you actually used."_
------------------------------------------------------
#### but why not making two socklen_t from the bieggning? 
- **1. `sizeof()` is a compile-time constant** The size of `struct sockaddr_in` is fixed (typically 16 bytes) and known before your program even runs. `sizeof(serv_addr)` is evaluated at compile-time and replaced with a fixed number. Creating a variable like `socklen_t serv_len` wastes stack memory to store a number that never changes and is only used once.
    
- **2. `bind()` takes a value, but `accept()` takes a memory address**
    
    - **`bind()` only reads:** It asks "how big is this data I am reading?" It takes the integer value directly, so `sizeof(serv_addr)` is sufficient.
        
    - **`accept()` writes back:** It asks "how much space do I have to write the client's info, and how much did I actually write?" Because C functions cannot write data back to a raw number like `16`, you **must** give `accept()` a real memory variable (`&clilen`) so it has a location to write into.
        

**Rule of Thumb for Sockets**

- **Pass `sizeof(...)` directly:** For functions where address size is purely an **input** (`bind()`, `connect()`).
    
- **Declare a `socklen_t` variable:** Only for functions that require a **pointer** (`socklen_t *`) to modify the size (`accept()`, `recvfrom()`, `getpeername()`).

#### why we use fork()?
Both **`recv()`** (network input) and **`fgets()`** (keyboard input) are **blocking functions**—they freeze program execution while waiting for input.

Without `fork()`, a single process gets stuck on whichever action comes first:

- **Stuck on `recv()`:** You cannot type or send a message until after the client sends you a message.
    
- **Stuck on `fgets()`:** You cannot receive incoming network messages until after you type something in the terminal and press Enter.


#### the point of two loops at the end
**Child Process Loop (Receiving)**

- **Role:** Dedicated entirely to receiving data coming from the connected client over the network.
    
- **Flow:**
    
    1. **`bzero(recvBuffer, ...)`**: Clears the memory buffer so previous messages don't bleed into new ones.
        
    2. **`recv(...)`**: Freezes (blocks) only the child process until a TCP packet arrives from the client. If `recv` returns `0` or `-1`, it detects a disconnect or error and exits the process.
        
    3. **`printf(...)`**: Prints the received message to your server console.
        
    4. **Repeat**: Loops back to `recv()` to wait for the next incoming network message.
        

**Parent Process Loop (Sending)**

- **Role:** Dedicated entirely to capturing local keyboard input and sending it across the network.
    
- **Flow:**
    
    1. **`bzero(sendBuffer, ...)`**: Wipes the outgoing buffer.
        
    2. **`fgets(...)`**: Freezes (blocks) only the parent process until you type a message in the terminal and hit `Enter`.
        
    3. **`send(...)`**: Takes your typed string and transmits it through `comminucation_sock` to the client (adding `+1` to include the null terminator `\0`).
        
    4. **`printf(...)`**: Prints confirmation ("Message sent!").
        
    5. **Repeat**: Loops back to `fgets()` to wait for your next typed message.
        

**Why This Setup Works:**

Because `fork()` split your code into two independent running processes, both `while(1)` loops execute at the exact same time. The child can sit blocked on `recv()` waiting for network packets, while the parent sits blocked on `fgets()` waiting for keyboard input—neither process stops or freezes the other.


#### why usign loops
- Keeps the Chat Session Alive, functions execute sequentially from top to bottom, without a loop, send() or recv() would execute exactly once, reach the end of the function, and close the program, the while(1) loop forces the processes to run infinitely so you can have an ongoing conversation.
- 
- Maintains Independent Input/Output CyclesBecause fork() split your program into two running processes, each process uses its loop to continuously repeat its specific job:Child Loop (Receiving): Blocks on recv() $\rightarrow$ receives packet $\rightarrow$ prints to screen $\rightarrow$ loops back to wait for the next packet.Parent Loop (Sending): Blocks on fgets() $\rightarrow$ captures typed text $\rightarrow$ transmits via send() $\rightarrow$ loops back to wait for your next typed message.
